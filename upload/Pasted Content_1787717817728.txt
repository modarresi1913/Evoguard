در ادامه نسخهٔ کامل و نهایی پرامپت را می‌بینی. نام **Behave to One: AI Edition** کاملاً حذف شده و نام محصول فقط **EvoGuard** است.

```text
نقش تو:

تو یک استراتژیست محصول در سطح جهانی، معمار نرم‌افزار، پژوهشگر مهندسی نرم‌افزار، متخصص AI-assisted software engineering و مشاور طراحی محصولات B2B SaaS هستی.

در حوزه‌های زیر تخصص داری:

- تولید و اصلاح کد با هوش مصنوعی
- ارزیابی کیفیت، امنیت و maintainability کد
- مهندسی نرم‌افزار تجربی
- تحلیل تاریخچهٔ Git
- تحلیل Pull Request و CI/CD
- مدیریت technical debt
- ردیابی منشأ تغییرات و provenance
- طراحی سیستم‌های قابل‌توضیح و evidence-driven
- تحلیل dependency و software supply chain
- طراحی سیاست‌های merge و code review
- طراحی محصولات enterprise
- زیست‌شناسی رفتار و مفهوم فشارهای محیطی
- استراتژی رقابتی و category creation
- تحلیل بازار و اعتبارسنجی محصول

مأموریت:

یک محصول نرم‌افزاری B2B SaaS به نام «EvoGuard» طراحی کن.

EvoGuard یک پلتفرم «Context-Aware AI Code Integration» است که تغییرات تولیدشده، اصلاح‌شده یا پیشنهادشده توسط هوش مصنوعی را پیش از merge شدن به codebaseهای موجود ارزیابی، توضیح و کنترل می‌کند.

شعار اصلی محصول:

Context before merge.

توصیف کوتاه محصول:

Evidence-driven control for AI-assisted code changes.

تعریف یک‌جمله‌ای محصول:

EvoGuard به تیم‌های مهندسی کمک می‌کند تغییرات AI-assisted را پیش از merge، با تاریخچه، قراردادها، وابستگی‌ها، تست‌ها، محدودیت‌های امنیتی و رفتار واقعی codebase مقایسه کنند.

────────────────────────
۱. زمینه و مسئله
────────────────────────

در عصر ابزارهای تولید کد با هوش مصنوعی، مشکل اصلی دیگر صرفاً تولید کد نیست.

مشکل اصلی این است که کد تولیدشده یا اصلاح‌شده توسط AI معمولاً از تاریخچه و فشارهای پنهان codebase آگاهی ندارد.

این فشارها ممکن است شامل موارد زیر باشند:

- incidentهای گذشته
- revert و rollbackهای قبلی
- dependencyهای deprecated
- wrapperهای داخلی
- قراردادهای معماری
- conventionهای نانوشتهٔ تیم
- محدودیت‌های تست
- شکست‌های CI
- رفتارهای حساس runtime
- نیازهای مشتریان قدیمی
- تصمیم‌های معماری ثبت‌شده در ADR
- تصمیم‌های معماری ثبت‌نشده
- محدودیت‌های امنیتی و compliance
- الگوهایی که در گذشته به technical debt یا outage منجر شده‌اند

یک قطعه کد ممکن است از نظر syntax و type درست باشد، اما همچنان با ecosystem پروژه ناسازگار باشد.

بنابراین EvoGuard باید پیش از merge شدن هر Pull Request مشخص کند:

1. این تغییر با کدام بخش‌های codebase سازگار یا ناسازگار است؟
2. کدام شواهد تاریخی یا فنی از این ارزیابی پشتیبانی می‌کنند؟
3. آیا الگوی مشابهی در گذشته به defect، incident، rollback یا revert منجر شده است؟
4. چه تست، approval، refactor یا بررسی امنیتی بیشتری لازم است؟
5. کدام قراردادها یا constraintهای پروژه در این تغییر رعایت نشده‌اند؟
6. آیا پیشنهاد اصلاحی وجود دارد؟
7. میزان اطمینان سیستم به هر نتیجه چقدر است؟

اصل اساسی:

EvoGuard نباید فقط وضعیت فعلی کد را بررسی کند؛ باید تاریخچه، زمینه و پیامدهای تغییر را نیز تحلیل کند.

۳. ارزیابی انتقادی ایده

ابتدا ایدهٔ EvoGuard را به‌صورت انتقادی بررسی کن.

این موارد را تحلیل کن:

2. چه نوع سازمان‌هایی بیشترین درد را دارند؟
3. آیا این مسئله به‌اندازهٔ کافی فوری است؟
4. آیا بازار هدف برای ساخت یک کسب‌وکار مستقل کافی است؟
5. کدام بخش ایده differentiated است؟
6. کدام بخش صرفاً استعاره یا feature تزئینی است؟

8. چرا GitHub Copilot، Cursor، CodeRabbit، Qodo، Snyk، SonarQube، Semgrep یا ابزارهای مشابه به‌تنهایی این مسئله را حل نمی‌کنند؟

10. آیا این مفهوم برای CTO و مدیر مهندسی قابل‌فهم و قابل‌خرید است؟
11. مهم‌ترین فرض‌های قابل‌ابطال چیست؟
12. چه چیزی ممکن است باعث شکست محصول شود؟
13. آیا مشتری حاضر است برای این محصول پول پرداخت کند؟
14. چه زمانی EvoGuard باید pivot کند؟
15. بهترین wedge اولیه برای ورود به بازار چیست؟

| فرض | اهمیت | احتمال نادرست‌بودن | روش اعتبارسنجی | معیار موفقیت | اقدام در صورت شکست |
|---|---:|---:|---|---|---|

سپس یک تحلیل صریح ارائه کن:

۸. مدل چندبعدی Change Compatibility Score
────────────────────────

به‌جای یک امتیاز مبهم، یک مدل چندبعدی و قابل‌توضیح طراحی کن.

نام امتیاز را انتخاب کن:

- ECS: Ecosystem Compatibility Score
- CCRS: Contextual Change Risk Score
- یا یک نام بهتر

نام انتخاب‌شده را با دلیل توضیح بده.

امتیاز باید حداقل این ابعاد را داشته باشد:

1. Contract Compatibility
2. Historical Compatibility
3. Dependency Compatibility
4. Test Compatibility
5. Convention Compatibility
6. Security Risk
7. Runtime Risk، در صورت وجود داده
8. Ownership and Review Risk
9. Architecture Compatibility

برای هر بُعد مشخص کن:

- تعریف
- ورودی‌ها
- الگوریتم محاسبه
- نوع evidence
- confidence
- severity
- false positiveهای محتمل
- false negativeهای محتمل
- روش اعتبارسنجی
- اقدام پیشنهادی

خروجی باید شامل score کلی و breakdown باشد.

نمونه:

```text
Overall compatibility: 74/100
Confidence: 0.86

Contract compatibility: 91/100
Historical compatibility: 62/100
Dependency compatibility: 58/100
Test compatibility: 83/100
Convention compatibility: 79/100
Security risk: Low
Ownership risk: Medium

Recommendation:
Review required

Top evidence:
- الگوی مشابه در دو Pull Request قبلی به rollback منجر شده است.
- API استفاده‌شده deprecated است.
- regression test برای timeout وجود ندارد.
- فایل تغییرکرده مالک مشخصی دارد اما owner review دریافت نکرده است.
```

یک فرمول اولیه ارائه کن، اما به‌صراحت بنویس که وزن‌ها باید با دادهٔ واقعی calibrate شوند.

مثلاً:

```text
Compatibility Score =
w1 * Contract Compatibility
+ w2 * Historical Compatibility
+ w3 * Dependency Compatibility
+ w4 * Test Compatibility
+ w5 * Convention Compatibility
+ w6 * Architecture Compatibility
- w7 * Security Risk
- w8 * Ownership Risk
```

توضیح بده چرا score نمی‌تواند تنها معیار merge باشد.

برای scoreهای مختلف policy پیشنهاد کن:

- ۹۰ تا ۱۰۰: low-friction merge
- ۷۰ تا ۸۹: merge با review عادی
- ۵۰ تا ۶۹: review اجباری یا تست تکمیلی
- کمتر از ۵۰: block یا approval ویژه

تأکید کن که این thresholdها جهانی و قطعی نیستند و باید با baseline هر repository و دادهٔ واقعی تنظیم شوند.

- reliability آن چقدر است؟
- چه نوع evidence تولید می‌کند؟
- false inference محتمل چیست؟
- آیا در MVP است یا بعداً اضافه می‌شود؟

برای Historical Event این schema را ارائه کن:

```text
HistoricalEvent
- id
- repository_id
- event_type
- affected_files
- affected_symbols
- pattern_signature
- failure_mode
- outcome
- severity
- evidence_refs
- valid_from
- valid_until
- confidence
- created_at
- updated_at
```

توضیح بده چگونه سیستم از یک رویداد تاریخی، constraint قابل‌استفاده برای PR جدید می‌سازد؛ بدون اینکه علت را بیش از اندازه از داده‌ها استنباط کند.

بین این سه سطح تفاوت روشن بگذار:

1. Observation
2. Inference
3. Policy

مثال:

```text
Observation:
این الگو در دو commit بعداً revert شده است.

Inference:
این الگو احتمالاً در این codebase پرریسک است.

Policy:
استفاده از این الگو نیازمند approval مالک سرویس است.
```

سیستم نباید inference را به‌عنوان fact قطعی نمایش دهد.

۱۰. Provenance و منشأ تغییرات
────────────────────────

یک مدل واقع‌بینانه برای provenance طراحی کن.

EvoGuard نباید ادعا کند که می‌تواند با قطعیت تشخیص دهد کدام خط توسط AI تولید شده است.

سیستم باید این حالت‌ها را ثبت کند:

- کد مستقیماً از یک ابزار AI اعلام‌شده آمده است.
- کد با AI اصلاح یا refactor شده است.
- کد از چند منبع ترکیبی آمده است.
- کد به‌صورت احتمالی AI-assisted است.
- منشأ کد نامشخص است.

سطوح provenance:

- declared
- inferred

2. assumptions
3. files changed
4. tests added or required

```
